## What happens when clicked

The click requests a cooperative stop of the advanced Xilinx package-generation loop. `FUN_014ec7c0` performs one operation: it writes `1` to byte field `+0x2371` of the `TCompilePackage` form. It does not call the VHDL DLL, stop a process, update the progress bar, append a log line, hide or disable a control, or close the form.

`FUN_014ecfb0` consumes the byte. Before it creates and compiles each next library, it tests `+0x2371`. If the value is nonzero, it appends a recovered resource string to the output memo, clears the byte to `0`, and leaves the item loop. It then refreshes the target-library list through `_Pkg_GetLibraryList` and returns normally.

This check is between package items. A package that has already entered `_Pkg_CompilePackage` is not interrupted by this flag. The recovered path contains no `TerminateProcess`, process-handle close, thread termination, DLL abort export, or cancellation callback from this handler.

## Request delivery and consumption

The advanced **Compile** handler calls progress helper `FUN_014ebef0` before the batch and after each completed item. The generator also calls it during a long source scan. This helper updates `cgProgressBar` and drains the application message queue. That message processing lets the speed-button click run while the otherwise synchronous workflow is at one of these progress points.

The next package-loop checkpoint consumes the request. Therefore:

- A request received before the first package stops the loop before `_Pkg_NewLibrary` for that package.
- A request received after one package's progress update stops before the next package.
- A request cannot undo packages that the loop completed before the checkpoint.
- The recovered caller does not show a checkpoint inside `_Pkg_CompilePackage`. A currently executing DLL call finishes or fails by its own behavior before this application loop can check the byte again.

## UI, log, and progress effects

- Immediate click effect: only the in-memory byte changes. The handler gives no visible acknowledgement.
- Consumer effect: the advanced worker appends one resource-backed abort-status line to the read-only output memo. The exact localized text behind `PTR_PTR_020011f0` is not present in the recovered C, so this article does not invent it.
- List effect: after the abort branch, the worker gets the current library list from `VHDL_DLL2.DLL` and replaces the target-library combo contents.
- Progress effect: the abort branch does not calculate another per-item percentage. After the worker returns, `FUN_014ecbc0` appends its normal post-worker resource line. In the recovered abort path, field `+0x2390` stays zero, so the caller also sets the progress bar to `100`.
- Control state: no recovered abort path disables, hides, changes, or re-enables `sbAbort`. The click does not change the **Compile**, **Select...**, target-library, or search-list controls.

## Idle, repeated, and late clicks

- `FormCreate` initializes `+0x2371` to zero.
- An idle click sets the byte even when no advanced batch is active. `FUN_014ecbc0` does not clear this byte when a new batch starts. If that batch has at least one package item, its first checkpoint consumes the old request and stops before the first library.
- If the package list is empty, `FUN_014ecfb0` does not enter the loop and does not clear the byte. The request remains armed.
- Repeated clicks before a checkpoint still store only byte value `1`. They do not queue multiple cancellations.
- The consumer clears the byte once and then exits the loop. A click that is delivered after the last useful checkpoint can remain set for the next advanced run.
- The simple **Select...** source-file path uses `FUN_014ec1f0`. It does not read `+0x2371`. Thus, this abort byte does not stop that recovered compile route and can remain armed for a later advanced batch.

## Partial output, cleanup, and errors

- Each normal iteration calls `_Pkg_NewLibrary` before `_Pkg_CompilePackage`. Abort is checked only before that pair. Libraries completed before the request remain in DLL-managed state; the abort path has no delete or rollback call.
- The abort branch does not create the next library. It skips all remaining items in the prepared list.
- Abort follows the normal function exit. The worker refreshes the library list and finalizes its local Delphi strings. The outer handler destroys its temporary generator object after the worker returns.
- If `_Pkg_CompilePackage` returns false, the worker builds a Delphi exception from its error buffer and raises it. This error path is separate from the abort byte. There is no local catch, retry, or abort-specific rollback in the recovered worker.
- An exception before the normal post-loop path can skip the list refresh and the outer final progress update. The recovered C does not establish all compiler-generated exception-unwind cleanup.
- The VHDL DLL owns the implementation of library creation and compilation. Its internal file names, atomicity, temporary-file cleanup, and behavior during an operating-system or DLL failure are outside the recovered application source.

## Analysis limits

- The recovered code proves cooperative cancellation only for `FUN_014ecfb0`, the advanced package loop used by `bPrimGen`. It does not prove cancellation support inside `VHDL_DLL2.DLL` or the simple source-file compile route.
- The exact abort and post-worker memo strings are resource pointers in the recovered C. Their text was not resolved in this pass.
- The outer handler's progress value of `100` is a UI assignment. It does not prove that all requested packages compiled after an abort.
